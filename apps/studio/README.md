# FDraft Studio (application)

The standalone Tauri + React + TypeScript desktop application — a genuinely separate program from FDraft: its own package (`@fdraft/studio`), its own entry point (`src/main.tsx` → `src-tauri/src/main.rs`), its own bundle identifier (`com.fdraftstudio.app`, distinct from FDraft's `com.burrichen.fdraft`), its own window title ("FDraft Studio"), its own app-data/config locations, its own tests, and its own build output/installer. It consumes `@fdraft/theme-sdk` and `@fdraft/theme-renderer` via the pnpm workspace link (the same packages `apps/renderer-lab` and eventually FDraft consume) and has no source dependency on the sibling FDraft application — enforced by `scripts/check-package-boundaries.mjs`.

## Commands

```
pnpm --filter @fdraft/studio dev            # Vite dev server only, http://localhost:5190
pnpm --filter @fdraft/studio tauri:dev      # the real desktop app, hot-reloading
pnpm --filter @fdraft/studio tauri:build    # real installers: .app + .dmg (macOS), etc.
pnpm --filter @fdraft/studio typecheck
pnpm --filter @fdraft/studio test
pnpm --filter @fdraft/studio build          # frontend only: tsc + vite build
pnpm --filter @fdraft/studio lint

# Rust backend, from apps/studio/src-tauri/:
cargo check
cargo fmt --check
cargo clippy --all-targets -- -D warnings
```

## Architecture: a thin Rust shell, testable TypeScript core

`src-tauri/` is deliberately minimal — it defines no custom Tauri commands at all, just wires up three official plugins (`tauri-plugin-fs`, `tauri-plugin-dialog`, `tauri-plugin-store`) that expose real OS filesystem/dialog access to the frontend. Every project-lifecycle behaviour (atomic save, autosave, crash recovery, snapshots, undo/redo, recent projects) lives in `src/` as plain TypeScript, built against a `StudioPlatform` interface (`src/platform/types.ts`) rather than calling Tauri APIs directly:

- `src/platform/tauriPlatform.ts` — the real implementation, used by the shipped app.
- `test/helpers/nodePlatform.ts` — a real `node:fs`-backed implementation used only in tests, so atomic-save/crash-recovery logic is exercised against genuine filesystem semantics (real `rename`, real `mkdir`) in a temp directory, without needing a Rust/Tauri runtime at all.

This is why `pnpm test` runs in milliseconds and needs no Rust toolchain, while still testing real file-level behaviour rather than a mock.

## Filesystem locations

| What | Where | Notes |
| --- | --- | --- |
| A project itself | Wherever the user chooses (a `.fdstudio` file, or an unpacked project directory) | Never inside Studio's own app-data — a project is portable, owned by the user. |
| Recent-projects list | `<app config dir>/recent-projects.json` | Studio's own config, not project content — see `src/recent/`. Capped at 10 entries (`MAX_RECENT_PROJECTS`). |
| Crash-recovery autosaves | `<app data dir>/recovery/<project-key>.fdstudio` + `.meta.json` | Never the project's own path — see "Autosave and crash recovery" below. |
| Named snapshots | `<app data dir>/snapshots/<project-key>/<snapshot-id>.fdstudio` + `.meta.json` | Capped at `MAX_SNAPSHOTS_PER_PROJECT` (20) per project, oldest pruned first. |

`<app data dir>`/`<app config dir>` are Tauri's real per-OS locations (`@tauri-apps/api/path`'s `appDataDir()`/`appConfigDir()` — e.g. `~/Library/Application Support/com.fdraftstudio.app` on macOS). `<project-key>` is a short hash of the project's own path (`src/project/paths.ts`'s `projectStorageKey`), so renaming a project doesn't orphan its recovery/snapshot history.

## Save safety

- **Atomic saves** (`src/project/atomicSave.ts`): a `.fdstudio` file is written to a temporary sibling, validated (re-unpacked through the SDK), then `rename`d over the destination — atomic on both POSIX and Windows. An unpacked project *directory* is written to a temporary sibling directory, validated, then swapped in: the old directory is renamed to a `.bak-*` sibling, the new one renamed into place, and only then is the backup removed — so a crash between those two renames leaves the original recoverable, never a half-written destination.
- **Autosave never touches the real save file.** It writes to a separate recovery slot only (`src/recovery/recovery.ts`), validated the same way a real save is. On next launch, Studio looks for a recovery entry newer than the project's own last save and prompts to recover or discard.
- **Named snapshots** (`src/snapshots/snapshots.ts`) are immutable point-in-time copies; "restore" always saves to a *new* path, never overwriting the current project.
- **Undo/redo** (`src/history/commandStack.ts`) is a generic command stack with transaction grouping (`beginTransaction`/`commitTransaction`) and a bounded history (100 entries, oldest dropped).
- **Moved/deleted project folders**: `isMissingPathError` (`src/project/projectSession.ts`) recognises `ENOENT`-shaped failures and surfaces a clear message rather than an unhandled crash; the recent-projects list separately flags entries whose path no longer exists (`checkRecentProjectPaths`) instead of failing to open them.

## Design Mode: the direct-manipulation editor

Design mode's canvas (`src/ui/canvas/Canvas.tsx`) is a real, tested editor, not a read-only preview — it renders an absolutely-positioned selection/handle overlay *on top of* the actual `@fdraft/theme-renderer` output (keyed off its `data-fdraft-layer-id` DOM markers), so there is no second/parallel rendering implementation to drift from FDraft's own runtime.

- **Editor logic** lives in `src/editor/` as plain, framework-free TypeScript, unit-tested without mounting anything: `layerTree.ts` (tree traversal/reparenting, cycle prevention), `geometry.ts` (rotation-aware bounding boxes, resize/rotate math, snap-line computation, transform rounding for stable JSON), `selection.ts`, `viewState.ts` (pan/zoom), `containerRef.ts` (page/popup/master addressing), and `layerCommands.ts` (~25 `Command<StudioProjectDocument>` factories — transform, opacity, crop, mask, z-order, lock/hide, rename, group/ungroup, duplicate/delete/paste, align, distribute, text).
- Every gesture (drag/resize/rotate) uses local "draft" state for live feedback and commits **exactly one** command on release — never hundreds of undo entries for one continuous drag. `ProjectSession.applyCommand`/`beginTransaction`/`commitTransaction` is the general entry point every edit goes through, so it all composes with the existing undo/redo stack.
- `src/ui/layers/LayersPanel.tsx` and `src/ui/properties/PropertiesPanel.tsx` are wired into the shell's existing Left/Right panels; a Focus mode (`src/ui/shell/StudioShell.tsx`) hides all chrome for a distraction-free canvas while staying fully editable, distinct from read-only Preview mode.

### Deferred (honestly incomplete, not silently dropped)

- **Copy Workspace**: no project-wide grouped/searchable copy-editing panel, placeholder-token insertion UI, or reset-to-default/duplicate/where-used/safe-replace yet. Text is editable per-layer today (double-click on canvas, or the Properties panel), but there is no dedicated Copy Workspace view, and no overflow/contrast/unresolved-placeholder warning system.
- **Guides and safe areas**: `@fdraft/theme-sdk`'s schema has no field for either yet. Adding one is a shared-contract change judged too significant to make unilaterally inside this phase — needs an explicit decision first.
- **Masks**: only none/rect/ellipse are offered. The schema's `MaskType` has no distinct "rounded-rect" variant (would need generated SVG path data), and asset-based masking needs an asset picker that doesn't exist yet.
- **Rich text**: plain text only; the allowlisted rich-text model (line breaks, emphasis, approved internal links) is not implemented.
- **Layer accessibility/description fields**: no such field exists in the layer schema; adding one was judged out of scope for a unilateral schema change here.
- The Properties panel's numeric fields don't live-resync while a layer stays selected through an *external* change (e.g. a canvas drag updates the document, but an already-open field keeps its value until you reselect) — a known rough edge from this codebase's established no-effect-resync pattern (`RightPanel.tsx`'s doc comment explains the same tradeoff for project metadata).
## Asset Workspace and import/export

`src/ui/assets/AssetWorkspace.tsx` is a fourth shell mode alongside Design/Behaviour/Preview: folders + tag/name search, grid and list views with transparency-checkerboard thumbnails, native multi-file import (`StudioPlatform.openFiles`) plus drag-drop and clipboard-paste, a detail panel with a real "where used" list, and an image-state-group editor (add/rename groups, add/remove/reassign states, toggle the default).

- **Import is content-addressed and never depends on the source file staying put.** `src/assets/assetImport.ts`'s `planAssetImport` validates extension/size, sanitises or rejects SVG (`sanitizeSvg`/`checkSvgSafety` from the SDK — strips scripts/handlers/`foreignObject`/external URLs/`@import`/entities, then re-validates and refuses to call anything clean unless it actually is), hashes the (possibly-sanitised) bytes, and detects duplicate content already in the project so re-importing the same file reuses the existing asset instead of creating a byte-identical duplicate. `src/assets/fileNames.ts` handles Unicode normalisation, Windows-reserved names, illegal characters, and display-name collisions — all purely cosmetic, since the actual storage path (`assets/<sha256><ext>`) never depends on the original filename at all.
- **The asset byte pool is additive-only during a session.** `mergeAssetBytes` (on `ProjectSession`) merges new/replaced bytes outside the undo-tracked command stack, so undoing a delete or a replace-source always finds its bytes still there; `src/project/projectFile.ts`'s `pruneAssetsToProject` resolves the pool back down to exactly what's referenced only at save/export time, which is also what makes a genuinely-missing asset surface as a real `MISSING_ASSET` error instead of silently vanishing.
- **`src/assets/assetCommands.ts`** is the same `Command<StudioProjectDocument>` pattern as the editor's layer commands: rename/move/tag/replace-source (keeps the asset id, so every layer reference and placed object's own position/properties survive untouched)/duplicate/delete, folders, and image-state-group editing — all undoable.
- **`src/project/exportAnalysis.ts`** (`analyzeThemeExport`/`analyzeProjectExport`) actually compiles and packs the project to get a *real* byte count before any file is written, alongside capabilities/required components/asset counts/warnings/blocking errors — shown in `ExportDialog.tsx` before the user commits. `src/project/projectFile.ts`'s `exportRuntimeTheme` (new — the SDK's `compileProjectToFdtheme` existed since Prompt 2 but nothing in Studio called it until now) writes atomically through the same `atomicWriteFile` machinery as every other save in this app: a failed export never touches a previously-exported file.
- **Native drag-and-drop**: `src-tauri/tauri.conf.json` sets `"dragDropEnabled": false` so the webview's standard HTML5 drop events (`DataTransfer.files`) reach the Asset Workspace instead of being intercepted by Tauri's native path-only drag-drop handler. This needs no new IPC plumbing and behaves identically in the browser dev harness and the shipped app — but **has not been verified against a real OS drag gesture on the actual desktop app** (see below).

### Deferred (honestly incomplete, not silently dropped)

- Real native OS drag-and-drop and clipboard-paste import are implemented (standard web APIs, no Tauri plugin needed for paste) but not device-verified — only checked against the browser dev harness, consistent with this project's screen-capture-safety policy. The next `pnpm tauri dev` session should confirm a real file drag/paste actually imports.
- Non-destructive image optimisation (`src/assets/imageOps.ts`'s `reencodeImage` — Canvas-based PNG/JPEG/WebP re-encode at a chosen quality, applied through the same undoable replace-source command) has no UI wired to it yet.
- The Asset Workspace's folders/detail side panels don't independently collapse the way Design mode's Left/Right panels do, so very small windows get cramped rather than reclaiming space.
- Rounded-rect and asset-based masks are still not offered in the Properties panel's mask editor (unchanged from Prompt 5).
- Duplicate-*content* detection during import silently reuses the existing asset rather than asking the user to choose — a defensible default, not the only reasonable one.
- Real component adapters mapped to FDraft — see `docs/architecture/RENDERER_HOST_NOTES.md` (Prompt 10).

## Pages, masters, components, and the FDraft Default Event template

Project navigation, master inheritance, the guaranteed FDraft template, component copy/zone editing, and a validation panel — see `docs/IMPLEMENTATION_STATUS.md`'s Phase 7 row for full evidence.

- **Page/popup/master CRUD** lives in `src/project/containerCommands.ts` (add/rename/duplicate/reorder/delete, all as `Command<StudioProjectDocument>` factories), wired into `src/ui/shell/LeftPanel.tsx`. Deleting a master checks `findMasterDependents` first and refuses if any page/popup still inherits from it; `wouldCreateMasterCycle` blocks a master from (transitively) inheriting from itself.
- **Master inheritance** is resolved once, in `@fdraft/theme-renderer`'s `resolveContainerLayers`/`resolveMasterChain`, and reused everywhere: real rendering, Studio's live preview, and "detach from master" (which deep-clones the *resolved* inherited layers with fresh ids via `buildDetachFromMasterCommand`). A page/popup can narrowly override one inherited master layer's `transform`/`visible`/`opacity` (never its content or type — themes never rewrite internals) via `masterLayerOverrides`, keyed by that master layer's own id so it never collides with the existing global `DUPLICATE_ID` check. `src/ui/shell/MasterInheritancePanel.tsx` exposes assign/override/reset/detach. Editing a master's own layers on canvas works by rendering it through a synthetic throwaway page (`Canvas.tsx`'s `MASTER_PREVIEW_PAGE_ID` sentinel), since `ThemeRenderer` can only target a real page or popup.
- **The FDraft Default Event template** (`src/templates/fdraftEventContract.ts`/`fdraftEventTemplate.ts`) is built directly from a registered page/component contract — 8 surfaces (Event Landing, Draft, Results, Completion, About/Information, Event Available, Join, Event Complete), every author-written string given a stable copy slot and an approved default. Its component metadata (required/singleton/compatible zones/minimum size) is balanced so the template produces zero `checkDesignWarnings` — this is asserted by a test, not just eyeballed.
- **Styling tokens**: `ShapeLayer.fillGradientTokenId`/`cornerRadiusTokenId`/`shadowTokenIds` and `TextLayer.fontWeightOverride`/`lineHeightMultiplier`/`letterSpacingPx`/`wrap` are resolved to CSS by `@fdraft/theme-renderer/src/tokenStyle.ts` — a layer only ever stores a token *id*, so one edit to a token updates every layer that references it. `src/editor/tokenCommands.ts` creates new color/gradient/border/radius/shadow tokens; `PropertiesPanel.tsx`'s `ShapeLayerFields` wires Fill-color and Corner-radius pickers with an inline "+ New…" quick-create (border/gradient/shadow picker UI is deferred — see below).
- **Component copy and zones**: a new, additive `ComponentCopyContractRegistry` (alongside the existing adapter registry, so no breaking change touched any of the 12 files that reference it) declares each component's editable copy slots — default text, required/optional, allowed placeholders, character guidance, accessible-name fallback. `resolveComponentCopy` never lets a *required* slot resolve to an empty string. `PropertiesPanel.tsx`'s `ComponentLayerFields` exposes a Zone dropdown (`ZoneKind`: header/sidebar/main/overlay/footer — a logical tag, not yet a resizable region) and one field per declared copy slot.
- **The Validation panel** (`src/ui/shell/ValidationPanel.tsx`) shows two genuinely separate channels: `checkSemantics`'s blocking errors (gate save/export) and `@fdraft/theme-sdk`'s new `checkDesignWarnings` — a non-blocking advisory channel covering missing required components (checked project-wide, not per-page — a bug caught and fixed before it shipped), duplicate singletons, incompatible zones, undersized components, low text-over-shape contrast (real WCAG contrast-ratio math), and decorative layers covering protected components (AABB-overlap + z-order heuristic, not true hit-testing). Design warnings get a "Go to" jump button; semantic errors are shown as plain text, since their path format isn't one this panel controls.
- **Starter templates** (`src/templates/starterTemplates.ts`): Standard FDraft (= the template above), Immersive, Minimal, Poster, Blank — every one a plain `StudioProjectDocument` built through the same schema/editor as any other project, no hidden one-off rendering path. `ProjectSession.newProjectFromTemplate` is a new method; `newProject`'s existing single-blank-page behaviour is unchanged. Picked from a new dropdown on the startup screen.

### Deferred (honestly incomplete, not silently dropped)

- **Responsive design** got the smallest share of this phase relative to its scope in the prompt: no true nine-point anchor *stretch* (opposing anchors resizing width/height), fixed/fill/hug sizing modes, a 4-sided margin concept distinct from per-anchor offset, min/max width/height constraints, proportional scaling across breakpoints, a Desktop/Laptop/Small-Window/Custom preview-profile switcher, or a responsive inspection mode comparing all standard sizes with direct navigation to warnings. Only single-edge/center anchoring and one-active-breakpoint transform overrides exist, both pre-dating this phase.
- **Zones are a logical tag only.** `ZoneKind` lets a component declare/require a zone and lets the validation panel flag a mismatch, but there is no visual, resizable header/sidebar/main/overlay/footer region editor.
- **Border/gradient/shadow token picker UI** in the Properties panel — the schema fields, renderer wiring, and token-creation commands all exist and are tested, but only Fill-color and Corner-radius got quick-create UI wired in this phase; each of the other three needs an existing `colorTokenId` and a good compound quick-create flow was judged out of budget.
- **Masks** are unchanged from Prompt 5/6: only none/rect/ellipse, no rounded-rect or asset-based option.
- **Accessibility auditing** beyond the contrast-ratio/AABB-overlap heuristics already built — no true hit-testing/DOM measurement, no keyboard-navigation-order check.
- Real FDraft component adapters remain unimplemented by design until Prompt 10 — Studio's 16 sample adapters are faithful stand-ins with sample data, never real domain logic.
- Per-OS installer CI (a full `tauri build` matrix) — CI runs `cargo check`/`clippy`/`fmt` and the frontend build/tests on every push; producing real installers is a separate, heavier workflow reserved for when Studio has something worth releasing.

## Behaviour Mode: no-code rules on a shared, deterministic evaluator

Behaviour Mode (`src/ui/behaviour/BehaviourWorkspace.tsx`) is a real rule-builder UI on top of a real evaluator — the exact same one `@fdraft/theme-renderer` exports and would run inside FDraft, never a Studio-only interpretation of what a rule does. See `docs/IMPLEMENTATION_STATUS.md`'s Phase 8 row for the full registry of variables/triggers/actions and test evidence.

- **The rule schema** (`@fdraft/theme-sdk`) is entirely closed and declarative: a `RuntimeVariable` is one of 16 named kinds (event status/active/available, opted-in, current page/popup, draft generated, progress/watched/target counts, event completed, performance tier, reduced motion, a per-layer `interactionFlag`, an `imageState`, a host-named `dateTime`) — never an expression, never arbitrary profile/filesystem/points/draft-generation/watch-state/eligibility access. `BehaviourTrigger` is either the continuous `whileTrue` case or one of 8 lifecycle/interaction edge triggers plus a general `conditionBecomesTrue`. `BehaviourAction` is one of 12 safe visual effects — `show`/`hide`/`setEnabled`/`setImageState`/`applyStyleOverride` (the same closed style-property allowlist an existing `ComponentStyleOverride` already uses)/`startAnimation`/`stopAnimation`/`restartAnimation`/`openPopup`/`closePopup`/`navigateToPage`/`selectCopyVariant` — never a call into an FDraft business action.
- **The evaluator** (`@fdraft/theme-renderer`'s `resolveActiveBehaviourRules`/`resolveTriggeredRule`) is a pure function of one `RenderState` snapshot: `whileTrue` rules are all resolved together every render (higher `priority` wins a conflict, equal priority breaks to the later-declared rule), producing both the actual visual overrides *and* a full `BehaviourResolution.trace` — every candidate rule for every contested target, whether it won, lost, was disabled, or its condition was false. Because rules never see each other's resulting overrides within one pass, the evaluator is a single non-recursive walk that cannot hang at runtime no matter what a theme declares; `@fdraft/theme-sdk`'s `checkBehaviourRules` catches the *authoring* mistake (a rule that reads and writes the same image-state group) as a static, non-runtime concern instead.
- **Real hover/focus/pressed/selected**, not a manual toggle: `LayerFrame` wires native pointer/focus/click events to an optional `onInteractionFlagChange` callback a host folds into the `RenderState` it re-supplies (`applyInteractionFlagChange` is the exported pure helper for that fold) — the renderer itself never keeps this as internal state, staying a pure function of props like everywhere else in its architecture. Behaviour Mode's live preview wires this up for real: hovering, tabbing to, or clicking an element in the preview genuinely drives an `interactionFlag` condition, exactly as FDraft's real runtime would.
- **The rule builder UI**: a rule list (enable/duplicate/reorder/delete, one readable sentence per rule via `src/behaviour/describeBehaviourRule.ts`), a fully recursive `ConditionEditor.tsx` (every condition node type, with "negate" as a checkbox at any depth rather than a separate tree shape for `not`), an `ActionEditor.tsx` (target pickers drawn from the real project), a live **Simulator** for the read-only render context (event status/active/available/opted-in/draft-generated/completed, progress/watched/target counts, performance tier, reduced motion), and a **Show trace** panel explaining exactly which rule won each contested target and why, for the current simulated state.
- **A tested Candy Bowl fixture** (`packages/theme-renderer/test/fixtures/candyBowl.test.ts`) proves an image-state group switches states at configured, boundary-exact `progressPercent` ranges through the real evaluator — the states and ranges are ordinary editable project content, not hard-coded logic anywhere in the renderer.
- **Two real bugs were caught and fixed by this phase's own tests**: `resolveTriggeredRule` originally never evaluated a `conditionBecomesTrue` trigger's own embedded condition (only the rule's separate gating condition), so such a rule would have fired unconditionally; and the initial `interactionFlag` variable was purely ambient ("whichever layer this is already attached to"), which is meaningless for a project-wide `whileTrue` rule with no such layer — fixed by adding an optional explicit `layerId` directly on the variable (backward-compatible; omitting it keeps the ambient per-layer meaning).

### Deferred (honestly incomplete, not silently dropped)

- No dedicated per-layer Interaction States editor in the Properties panel (author hover/focus/pressed/disabled states directly on one selected layer) — the schema field, evaluator, and DOM wiring all exist and are tested; Studio only reaches this capability today through project-wide Behaviour rules, a more general but different authoring surface.
- `startAnimation`/`stopAnimation` (`whileTrue` rules) now have a full visual effect as of Prompt 9; `restartAnimation` and every other imperative action still only resolve as data pending the live click-dispatch work below.
- Clicking something in Studio's live preview doesn't yet dispatch into `resolveTriggeredRule` to perform a real on-screen popup-open/close, page navigation, or animation restart — the resolver itself is correct and unit-tested, but Studio hasn't wired the live click-through loop. Continuous rules (including real hover and, now, animation start/stop) are fully live today; edge-triggered navigation/popup/restart actions are not yet demonstrated end-to-end in Studio's own preview.
- Rule priority reordering uses up/down buttons, not drag-and-drop (functionally equivalent).
- Removing a rule's last action is silently prevented (the schema requires at least one) rather than disabling the button in the UI.

## Animations and effects: one shared, deterministic implementation

Prompt 9 filled in the two areas `@fdraft/theme-renderer` had reserved since Prompt 3 (no animation playback, effect layers as placeholder shells) — see `docs/IMPLEMENTATION_STATUS.md`'s Phase 9 row for the full registry of presets/effect kinds and test evidence.

- **Effect layers**: `LayersPanel` gained a "+ Effect…" control creating a full-canvas effect layer of any of the 11 kinds (rain/snow/fog/leaves/dust/stars/embers/confetti/fireflies/film grain/clouds) above existing siblings — send-to-back with the existing Arrange controls if it should sit behind the UI instead. This was Studio's *first* generic "add a new layer" affordance of any kind (`src/editor/effectCommands.ts`) — Design Mode previously had no way to create a layer from scratch at all, only duplicate/paste/template content; deliberately scoped to effects only, since that's what this prompt needed, not backfilled for every layer type.
- **Effect and animation editing**: `PropertiesPanel`'s `EffectLayerFields` (intensity/speed/direction/size-range/opacity/seed) and per-layer **Animations** section (trigger/preset/duration/delay/easing/repeat/direction/intensity/random-offset, via `src/editor/animationCommands.ts`) are real, undoable, and tested end-to-end (a genuine `EffectAndAnimationEditing.test.tsx` UI test adds an effect layer, edits its intensity, adds an animation, changes its preset/trigger, and deletes it).
- **A real Performance Inspector** (`src/performance/performanceInspector.ts` + `PerformanceInspectorPanel.tsx`, opened from a new "Performance" TopBar button) reports total/animated-layer counts, each effect layer's real tier-capped approximate particle count, large-asset count, and the same shared `checkDesignWarnings` feed the Validate panel uses — worded throughout as approximate structural counts, explicitly never a measured frame rate or hardware benchmark.
- **Reduced-motion and performance-tier preview are now real, stateful controls in the main status bar** — previously `hostSettings` was a hardcoded constant only reachable inside Behaviour Mode's own separate simulator. Toggling "Preview reduced motion" or the tier dropdown now visibly changes the actual Design/Preview mode canvas — verified with a real end-to-end test that adds a live animation, confirms it's playing, toggles reduced motion, and confirms the animation style disappears (and reappears when toggled back), plus a second test confirming the Low tier removes effect `<canvas>` elements from the DOM entirely.
- **Three real bugs were caught and fixed by this phase's own tests**: moving master-inheritance resolution into a place where the new effect-layer cap could be computed once per render initially broke the circular-master-chain error fallback (the resolution call ended up outside `RenderErrorBoundary`'s actual descendant tree) — fixed by introducing a `RenderedStage` descendant component in `@fdraft/theme-renderer`, mirroring its existing `ThrowRenderError` pattern; a `document`-variable-shadowing bug in that same package's `PageStage.tsx` (the renderable-document context value is also named `document`); and `usePlaybackGate`'s initial focus state relying on `document.hasFocus()`, which is unreliably `false` in the very environment used to test it.

### Deferred (honestly incomplete, not silently dropped)

- No UI exists to hand-author a *custom* keyframe list — the schema, the renderer's CSS generation, and dedicated renderer tests all fully support up to 12 keyframes; Studio's Animations section only offers the 10 built-in presets.
- No automated wall-clock performance-timing budget assertions — deliberately, since timing-based test assertions are flaky on shared CI runners. The enforced budget is structural (fixed per-tier particle/effect-layer/DPR caps in `@fdraft/theme-renderer`), verified with deterministic unit tests instead.
- High-DPI canvas scaling is implemented and unit-tested but was not verified against a real physical high-DPI display, only a headless Chromium run at device-pixel-ratio 1.
- Audio was deliberately not touched anywhere in this phase, per the prompt's own explicit instruction.

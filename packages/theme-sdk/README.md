# `@fdraft/theme-sdk`

The framework-neutral contract shared by FDraft Studio and FDraft: data model, schemas, validation, migrations, package formats, security limits, and a compiler from editable project to runtime theme. No React, no Tauri, no DOM, no FDraft business logic — see `docs/architecture/TWO_REPOSITORY_ARCHITECTURE.md`.

## Three entry points, by runtime requirement

- **`@fdraft/theme-sdk`** (main) — data model, validation, migration, compile. Genuinely universal: no `node:crypto`, `node:fs`, or Node-only APIs anywhere in its import graph, so it's safe to import from a browser bundle (a fixture lab, Studio's Tauri webview, FDraft's client code). `createId()` uses the standard `crypto.randomUUID()` global rather than `node:crypto` for exactly this reason.
- **`@fdraft/theme-sdk/packaging`** — pack/unpack/inspect/verify for `.fdstudio`/`.fdtheme` archives, plus the ZIP and sha256 primitives underneath them. Also universal — hashing uses the standard Web Crypto `crypto.subtle.digest` (async, hence every function here is `async`), not `node:crypto`, so this works directly in a browser/webview too (Studio's frontend packs and unpacks `.fdstudio` files itself, no Rust command needed). Still a separate entry point from the main module for conceptual separation (data model vs. archive format), not because it's Node-only.
- **`@fdraft/theme-sdk/node`** — the one genuinely Node-only entry point: filesystem helpers (reading/writing an unpacked project directory via real `node:fs`, for Git-diffable dev mode). Used by the CLI. A browser/webview host reimplements the equivalent directory walk against its own fs API and hands the resulting bytes to `@fdraft/theme-sdk/packaging`'s `buildFdstudioFileSet`/`finalizeFdstudioFileSet` instead.

## What's here

- **Data model** (`src/schema/`) — Zod schemas (source of truth) for the editable Studio project and the compiled runtime theme: tokens, pages/popups/masters with inheritance (a page/popup may narrowly override one inherited master layer's `transform`/`visible`/`opacity` via `masterLayerOverrides`, keyed by that master layer's own id — never its content or type), every layer type (image, text, shape, effect, component, slot, group; `ShapeLayer` also carries `fillGradientTokenId`/`cornerRadiusTokenId`/`shadowTokenIds`, `TextLayer` carries `fontWeightOverride`/`lineHeightMultiplier`/`letterSpacingPx`/`wrap`, `ComponentLayer` carries an optional `zoneKind` — header/sidebar/main/overlay/footer — plus per-slot `copyOverrides` and named `copyVariants`, each with its own stable id a Behaviour rule selects by), transforms/crop/mask, responsive anchors, assets and image-state groups, editor-only asset folders/tags/display-name (`AssetRecord.name`/`originalFileName`/`tags`/`folderId`, `AssetFolder` — stripped by `compileTheme` before anything reaches a runtime theme), component requirements with a closed safe-style-property allowlist (enforced both at validation time and defensively by the renderer) plus optional `singleton`/`compatibleZoneKinds`/`minWidthPx`/`minHeightPx` metadata, and declarative conditions/interaction-states. Every referenceable object carries a stable UUID. An optional `canvas` size (default 1920x1080) gives layer transforms a coordinate space to scale from. Generated JSON Schema lives in the repo-root `schemas/` — see that directory's README.
- **Animations and effects** (`AnimationDeclaration`/`EffectDeclaration` in `src/schema/interaction.ts`) — closed, bounded, no-code motion and particle configuration; `@fdraft/theme-renderer` is the one shared implementation that actually plays/draws them. `AnimationDeclaration.motion` is either `{type: "preset", preset}` (10 built-in shapes: `fade`/`rise`/`fall`/`slideLeft`/`slideRight`/`scalePop`/`float`/`wobble`/`pulse`/`sway`) or `{type: "keyframes", keyframes}` (up to 12 hand-authored steps of opacity/x/y/rotationDeg/scale) — the legacy single-property `property`/`from`/`to`/`loop` shape is still accepted for already-serialised data. `repeat` is `once`/`count` (≤100)/`infinite` — unbounded is always the explicit, visible choice, never a very large number standing in for it — with `direction` (normal/reverse/alternate), `intensity` (0-2, scales a preset's amplitude), and a bounded, seeded `randomOffsetMs` (≤2000ms) start-delay jitter. `AnimationTrigger` is `onEnter`/`onExit` (self-triggering from the layer's own mount/unmount) or `manual` (only ever started by a Behaviour rule's `startAnimation`/`restartAnimation` — how hover/focus/pressed-triggered and rule-gated idle animations are built, with no extra schema surface needed). `EffectDeclaration.kind` is a closed 11-value set (`rain`/`snow`/`fog`/`leaves`/`dust`/`stars`/`embers`/`confetti`/`fireflies`/`filmGrain`/`clouds`) with `intensity` (0-1, *never* a raw particle count — see the renderer's per-tier caps), `speed`, `directionDeg`, a bounded `sizeRange`, `opacity`, an optional `colorTokenId`, and a `seed` for deterministic, reproducible particle fields.
- **Behaviour rules** (`src/schema/behaviour.ts`, plus `RuntimeVariable`/`ComparisonOperator` and three new `Condition` node types in `src/schema/interaction.ts`) — a closed, no-code rule engine: `RuntimeVariable` is one of 16 named, presentation-safe values (event status/active/available, opted-in, current page/popup, draft generated, progress/watched/target counts, event completed, performance tier, reduced motion, a per-layer `interactionFlag` — hover/focus/pressed/selected, with an *optional* explicit `layerId` since a project-wide rule has no ambient "current layer" the way a per-layer `InteractionState` does — an `imageState`, and a host-named `dateTime`); deliberately excludes unrestricted profile records, filesystem access, points mutation, draft generation, watch-state mutation, and eligibility decisions. `Condition` gained `compare`/`inRange`/`boolean` nodes over these variables, alongside the pre-existing `always`/`eventPhase`/`stateEquals`/`and`/`or`/`not`. `BehaviourTrigger` is either the continuous `whileTrue` case, one of 8 page/popup/interaction lifecycle edges, or a general `conditionBecomesTrue`. `BehaviourAction` is one of 12 closed, purely presentational effects (`show`/`hide`/`setEnabled`/`setImageState`/`applyStyleOverride`/`startAnimation`/`stopAnimation`/`restartAnimation`/`openPopup`/`closePopup`/`navigateToPage`/`selectCopyVariant`) — none can call an FDraft business action. `BehaviourRule` (id/name/enabled/priority/trigger/condition/actions) lives project-wide on `StudioProjectDocument.behaviourRules`/`RuntimeThemeDocument.behaviourRules`. `@fdraft/theme-renderer`'s `resolveActiveBehaviourRules`/`resolveTriggeredRule` are the one shared, deterministic evaluator — see that package's README.
- **Validation** (`src/validation/`) — schema validation with path-specific issues, plus semantic checks (duplicate ids, broken references — including an asset's `folderId` and a folder's `parentId` — circular master inheritance, disallowed component style properties, and now every Behaviour rule's trigger/action targets) and an SVG safety policy: `checkSvgSafety`/`isSvgSafe` (reject-only, a regex blocklist) and `sanitizeSvg` (strips what can be safely stripped — `<script>`, `on*` handlers, `foreignObject`, external/`javascript:` URLs, `@import`, custom XML entities — then re-validates the result and refuses to call it clean unless every check actually passes; never silently ships something merely "better than before"). `checkBehaviourRules` (`src/validation/behaviourSemantics.ts`, folded into `checkSemantics`) catches impossible references, type mismatches (a numeric operator on a boolean variable, a boolean check on a numeric one, a compared value of the wrong type), unsafe actions (hiding/disabling a *required* component, a disallowed style property), and an obvious self-trigger loop (a rule that both reads and writes the same image-state group, which can never stabilise). A separate, non-blocking `checkDesignWarnings` (`src/validation/designWarnings.ts`) is an advisory channel a host can surface alongside semantic errors without gating save/export on it: missing-required-component detection (checked project-wide across every container, not per-page), duplicate singletons, incompatible zones, undersized components against a requirement's declared minimum size, WCAG contrast-ratio math (`contrastRatio`, also exported directly) for overlapping text-over-shape pairs, an axis-aligned-bounding-box-overlap-plus-z-order heuristic for a decorative layer covering a protected component, and `HOVER_ONLY_DISCOVERY` (a layer only ever revealed by a hover-based interaction state, with no equivalent focus-based state reaching the same content) — none of these are true hit-testing or DOM measurement.
- **Migration** (`src/migration/`) — an explicit registry of one-version-at-a-time upgrades, with future-major-version and too-old-legacy-version rejected outright rather than guessed at.
- **Packaging** (`src/packaging/`, exported via `@fdraft/theme-sdk/packaging`) — `.fdstudio` (editable project + assets) and `.fdtheme` (compiled runtime-only) package formats: deterministic ZIP (`fflate`), content-addressed asset paths (`computeAssetPath`), canonical (sorted-key) JSON, sha256 manifests, and archive security (zip-slip, file-count/size/compression-ratio limits, dangerous-extension and external-URL rejection). `compileProjectToFdtheme` is the one-call convenience (`compileTheme` + `packFdtheme`) a host reaches for.
- **Compile** (`src/compile/`) — turns a validated Studio project into a runtime theme: strips editor-only state (including the asset-organisation fields above), prunes unreferenced asset bytes, detects declared capabilities/required components. `findAssetUsage`/`collectUsedAssetIds` (exported from the main entry point) are the single source of truth both `compileTheme` and a host's own "usage count"/"where used"/"unused asset" UI build on — they can never silently disagree about what counts as used. Universal (main entry point) — compiling doesn't need hashing, only packing the result does.
- **CLI** (`src/cli.ts`, bin `fdraft-theme`) — `validate`, `inspect`, `verify`, `pack`, `unpack`, `compile`.

## Package formats

Both are ZIP archives with the given extension and a `manifest.json` at the root declaring file hashes for everything else in the archive.

```
.fdstudio                          .fdtheme
├── manifest.json                  ├── manifest.json   (= the runtime theme's own manifest: format
├── project.json                   │                      version, min renderer version, required
└── assets/                        │                      component keys, capabilities, file hashes)
    └── <sha256>.<ext>             ├── theme.json      (tokens, pages, popups, masters, assets
                                    │                      records, image-state groups, component
                                    │                      requirements — no editor state, ever)
                                    └── assets/
                                        └── <sha256>.<ext>   (only assets the compiled theme
                                                               actually references)
```

An unpacked-directory form of `.fdstudio` (same files, on disk instead of zipped) is supported for Git-diffable development — see `src/packaging/nodeFs.ts` and `fixtures/projects/sample-event/`.

## Commands

```
pnpm --filter @fdraft/theme-sdk typecheck
pnpm --filter @fdraft/theme-sdk test
pnpm --filter @fdraft/theme-sdk build
pnpm --filter @fdraft/theme-sdk generate:schemas   # regenerate schemas/*.schema.json
pnpm --filter @fdraft/theme-sdk check:schemas      # CI-safe drift check
pnpm --filter @fdraft/theme-sdk cli -- validate <path>
```

## Versioning and distribution

Pre-1.0 (`0.1.0`) — the contract is still experimental. Released as an immutable, checksummed tarball attached to a tagged GitHub Release (not a package registry) — see `docs/architecture/COMPATIBILITY_AND_RELEASES.md` for why, and `.github/workflows/release-theme-sdk.yml` for how.
